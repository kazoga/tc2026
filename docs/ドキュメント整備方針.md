# ドキュメント整備方針

## 1. 目的

本書は、このリポジトリで扱う文書の種別、種別ごとの配置・章立て・記載粒度・更新方針を定める。

文書が増えるほど「どこに書くか」「どこまで書くか」「いつ消すか」の判断がぶれ、同じ内容が
複数箇所に分散する。種別を先に決め、種別ごとに責務を固定することでこれを防ぐ。

文体・言語・配置の基本規約は `CLAUDE.md` を、詳細設計書の書き方は
`.claude/skills/design-doc-template` を正とする。本書はそれらの上位にある「文書の分類」を定める。

---

## 2. 文書種別

このリポジトリで扱う文書は次の 6 種別に分類する。どの種別にも当てはまらない文書は作らない。

| 種別 | 役割 | 配置 | 寿命 |
| --- | --- | --- | --- |
| 規約 | 従うべき規則を定める | `docs/` | 恒久。改訂して使い続ける |
| アーキテクチャ設計 | 複数パッケージにまたがる構造と責務分担 | `docs/` | 恒久。現状に追従させる |
| 詳細設計書 | 1 パッケージの内部設計 | `src/<pkg>/docs/` | 恒久。現状に追従させる |
| 運用手順 | 導入・起動・操作の手順 | `README.md` / `src/<pkg>/README.md` | 恒久。現状に追従させる |
| 検討記録 | 選択肢を比較して決めた判断とその理由 | `docs/` または `src/<pkg>/docs/` | 恒久。判断が覆るまで残す |
| 検証記録 | ある時点で実施した評価・計測の結果 | `docs/reviews/<対象>_<YYYYMMDD>/` | 追記も修正もしない |

### 2.1 恒久文書と凍結文書の区別

上表の上 5 種別は**現状を書く**文書であり、実装が変われば書き換える。

検証記録だけは**その時点の観測を書く**文書であり、後から書き換えない。実装が変わったら
新しい日付のディレクトリを作る。古い記録を「現状と違う」という理由で修正してはならない。
観測記録としての価値が失われる。

---

## 3. 種別ごとの章立てと粒度

### 3.1 規約

**目的**: 個別の事例ではなく、判断の原理を与える。読み手が未知のケースに直面したときに
自力で判断できる状態にする。

**章立て**:

```
1. 目的        なぜこの規約が要るか。規約が無いと何が起きるか
2. 定義        規約が扱う対象の分類
3〜n. 規則      分類ごとの規則。各規則に理由を添える
n+1. 例外       既定から外れるものと、その理由
n+2. 手順       新規追加時に踏む手順
```

**粒度の原則**: **個別対象の一覧表を作らない。** 一覧表は実装から必ず乖離する。個別の性質は
対象そのもの（`.msg` のコメント、設定ファイルのコメント）に宣言させ、規約は導出規則だけを
持つ。

例: `docs/トピック通信規約.md` は QoS を topic ごとに列挙せず、配信様式から QoS を導出する
規則だけを定め、個々の配信様式は `.msg` の先頭コメントに宣言させている。

### 3.2 アーキテクチャ設計

**目的**: パッケージ間の責務分担、データの流れ、境界の定義を示す。

**章立て**:

```
1. 目的と対象範囲
2. 全体構成         パッケージ一覧と責務
3. データフロー      topic/service を軸にした流れ
4. 境界の定義        パッケージ間で何を約束するか
5. 各パッケージの責務
6. 設計上の制約と前提
7. 未解決事項
```

**粒度の原則**: パッケージ内部の実装には踏み込まない。それは詳細設計書の役割である。
「どのパッケージが何を担い、何を約束するか」までを書く。

### 3.3 詳細設計書

**目的**: 1 パッケージの内部設計を、実装を読まずに把握できる状態にする。

**章立て**: `.claude/skills/design-doc-template` の雛形に従う。該当しない章は「該当なし」と
明記するか、省略理由を書く。

**粒度の原則**: クラス名・関数名の列挙はしない。それはコードとドキュメントの二重管理になり、
必ず乖離する。書くべきは**コードを読んでも分からないこと**に限る。

- なぜその構造を選んだか
- どの制約があってその実装になっているか
- 外部との契約（topic / パラメータ / ファイル形式）
- 状態遷移と例外条件

### 3.4 運用手順

**目的**: 読み手が手順どおりに実行すれば動く状態にする。

**章立て**:

```
1. 概要        このパッケージが何をするか（3 行以内）
2. 前提        依存、必要なハードウェア、事前設定
3. ビルド
4. 起動        代表的な起動方法
5. パラメータ   利用者が変更しうるものだけ
6. 確認方法     動いていることをどう確かめるか
7. 関連文書     設計書へのリンク
```

**粒度の原則**: README に設計を書かない。設計は詳細設計書へ置き、README からリンクする。
README が 300 行を超えたら、設計が混入していないか点検する。

### 3.5 検討記録

**目的**: 「なぜこの方式を選んだか」を残し、同じ検討の繰り返しと、理由を知らない差し戻しを
防ぐ。

**章立て**:

```
1. 決定事項     結論を先に書く
2. 背景        何を解決しようとしたか
3. 選択肢      比較した案
4. 判断基準     何を優先したか
5. 採用理由
6. 採用しなかった案と、その理由
7. 判断を見直す条件
```

**粒度の原則**: 検討の**時系列**ではなく**判断構造**を書く。「最初に A を試したが駄目だったので
B にした」は経緯であり、書くべきは「B を採用した。A は〈理由〉により要件を満たさない」である。

「7. 判断を見直す条件」を必ず書く。前提が変わったときに判断を再検討できる状態にする。

### 3.6 検証記録

**目的**: ある時点で何を確認し、何を確認していないかを残す。

**章立て**:

```
1. 実施日と対象     日付、対象コミット、作業ツリーの状態
2. 実施条件        環境、パラメータ、投入した入力
3. 確認項目と結果
4. 未確認事項      実施しなかったこと、できなかったこと
5. 生成物         ログ・計測データの配置
```

**粒度の原則**: **未確認事項を必ず書く。** 「何を確認したか」と同じだけ「何を確認していないか」
が重要である。これが無い検証記録は、読み手に過剰な信頼を与える。

結果は解釈ではなく観測値を書く。「良好だった」ではなく「到達時間 101.1 秒、残存プロセス 0」。

## 4. 書いてはならないこと

### 4.1 編集・見直しの経緯

**文書に作業プロセスを残さない。** 対象は次のとおり。

| 書かない | 理由 |
| --- | --- |
| 改版履歴の表・章 | git が持つ情報の劣化コピーになる |
| 「指摘を受けて修正した」「レビュー結果を反映」 | 読み手にとってノイズであり、文書の寿命を通じて陳腐化する |
| 「当初は〜としていたが」「従来は〜だったが」 | 現在の仕様だけが必要。過去の案は検討記録の「採用しなかった案」へ |
| 「〜を追記した」「〜に変更した」 | 差分は git diff が示す。文書は結果だけを書く |
| 「対応済み」「今回の修正で」 | 作業単位への言及であり、文書の寿命と一致しない |
| セッション中のやり取り | 会話の経緯は文書の読み手には無関係 |

**書き換え方**: 経緯の記述は、次のいずれかへ変換して残すか、削除する。

```
削除前: 当初は JSON で配信していたが、スキーマが実装にしか存在しないという指摘を
        受けて型付きメッセージへ修正した。

書き換え後（設計書）:
        融合状態は型付きメッセージで配信する。

書き換え後（検討記録の「採用しなかった案」）:
        std_msgs/String に JSON を載せる方式は採用しない。スキーマが送信側の
        実装にしか存在せず、購読側が独自に検証を実装することになるため。
```

判断の**理由**は残す。理由は現在の仕様を支える情報であり、経緯ではない。

### 4.2 その他

- リポジトリ外の絶対パス
- コードから自明な内容の言い換え
- 他文書と重複する内容（リンクで参照する）

## 5. 命名と配置

### 5.1 ファイル名

- 日本語名を基本とする。内容を表す名詞句にする。
- 作業単位を名前に含めない。`_phase1` `_完全版` `_input` `_開発指示書` のような、実装完了後に
  意味を失う語を使わない。
- 同一対象の文書を複数作る場合は、種別で分ける。
  `route_follower_詳細設計書.md` と `route_follower_検討記録.md` のように分け、
  phase や版で分けない。

### 5.2 配置

`CLAUDE.md` の規約に従う。

- ワークスペース全体に関わる文書 → `docs/`
- 特定パッケージに閉じる文書 → `src/<pkg>/docs/`
- 検証記録 → `docs/reviews/<対象>_<YYYYMMDD>/`
- メーカー資料・外部仕様 → `docs/references/`

判断に迷う場合は「この文書はパッケージを削除したら一緒に消えるか」で判断する。消えるなら
`src/<pkg>/docs/`、残るなら `docs/`。

### 5.3 パッケージごとの必須文書

| 文書 | 必須条件 |
| --- | --- |
| `README.md` | 全パッケージ。interface 定義のみのパッケージも含む |
| `docs/<名前>_詳細設計書.md` | ノードまたは非自明なロジックを持つパッケージ |

interface 定義のみのパッケージ（`tc_*_msgs`）は、README でメッセージ一覧と用途を示す。
各メッセージの配信様式・レートは `.msg` のコメントに書き、README では重複させない。

---

## 6. 作業単位の文書の扱い

実装の指示・入力として作られた文書（`_input`、`開発指示書` など）は、実装が完了した時点で
役目を終える。成果物である設計書が正になるため、次のいずれかを行う。

1. 設計書へ未反映の内容があれば、設計書へ移す
2. 判断の理由が含まれていれば、検討記録へ移す
3. 上記を終えたら削除する

「後で参照するかもしれない」を理由に残さない。git 履歴から復元できる。
