評価日: 2026-09-22。評価対象: HEAD `8023dd57f434417442a3e7d87062ecd2eaab60cd` のソフトウェア・設定。評価前の作業ツリーはクリーン。ロボットの起動・移動・制御指令送信は行っていない。

## P0-1の修正状況（2026-09-22追記）

P0-1の設定・制御ロジックの不整合は修正済み。ユーザー指定に従い、直進加速度を0.7 m/s²、直進減速度を1.5 m/s²に分離した。以下の評価本文とprobe_results.jsonは修正前の記録として残す。P0-2以降は未解決。

YPSpurは加減速で同じ制限値を使うため、ドライバがcoordinatorの平滑化後速度指令を読み、加速時0.7・減速時1.5へ切り替える。前後反転時は指令がゼロになってから逆向きに0.7で加速する。UI・自律・ジョイスティックすべてに適用される。

icart-middle.paramのMAX_ACC_V=1.5はcoordinator上限として維持。元ファイルの全数値・車輪半径の符号・トレッド・ギヤ比・ゲインは保持し、上限と運用値の関係をコメントで追記した。MAX_VEL=1.1に対し運用速度は1.0 m/s。MAX_W=1.0を踏まえ、上位とドライバの角速度上限も1.0 rad/sに整合。角加速度は0.6 rad/s²を維持。

上位制御にmax_decel_v=1.5を追加し、加速度から停止距離を計算しないようにした。実速度・直前指令の大きい方から、v²/(2a)に遅延走行距離を加えて判定する。標準の遅延予算は0.2秒＋制御1周期0.05秒。1 m/sでは制動0.333 m＋遅延0.25 m＋障害物余裕0.5 m＝約1.083 mが基準。目標点にも残距離に応じた速度上限を適用する。

ドライバは起動時に実際のcoordinatorからMAX_VEL/MAX_W/MAX_ACC_V/MAX_ACC_Wを取得し、上限超過なら起動失敗とする。実効値の/motion_limitsを上位に周期通知し、不一致・未受信・0.5秒の途絶時は自律出力をゼロにする。実機のUI/CLIで有効、YPSpurのないシミュレーション構成では明示的に無効化する。

検証: 関連Pythonテスト133件、C++制御分岐テスト1件成功。さらに実機の通信先と分離したIPC/DDSと--without-deviceのcoordinatorで、実際のicart-middle.param読込、加速、制動、逆転、指令タイムアウト停止、上限超過拒否を検証。実機接続・実機移動は行っていない。

停止距離の式は一定減速度と遅延予算による設計モデル。実機の路面・荷重・トルク制限下で1.5 m/s²が得られること、実遅延が予算内であることは未測定であり、実測前に制動性能確認済みとは扱わない。停止位置の大会判定や旋回中の車体領域保護は、別の未解決項目として残る。

検証コード: src/robot_navigator/tests/test_braking.py、test_motion_contract.py、src/ypspur_ros2/tests/test_motion_profile.cpp、verify_without_device.py。結果は[p01_validation.json](p01_validation.json)を参照。

## 修正前評価の結論

低速実機制御、経路追従、GNSS/LIO融合、手動・自動切替の基盤はある。ただし、必須課題の完走を保証できる段階ではない。停止距離の設定不整合、回避幅の上限違反、状態と停止指令の連携を先に直し、その上で停止線・道路端・待機列・ゴールを大会の意味に合わせて実装する必要がある。

HWの選定・機構・寸法適合・センサ追加は対象外。車体領域を使うソフトウェアの判定は対象に含める。以下のP0は自律走行の再試験前、P1は確認走行・本走行に向けた必須事項、P2は運用と検証の改善。これは開発上の優先度であり、公式の分類ではない。

## 実装済みの基盤

- YPSpurの新しいLinux向け公式修正、車輪パラメータの配置、起動時の速度・加速度設定が入っている。低速ジョイスティック操作は前回ユーザーが実機で確認済み。
- YPSpurの速度指令タイムアウト0.5秒、muxの指令鮮度監視、navigatorの姿勢・オドメトリ監視がある。融合経路では推定更新途絶時の停止もある。
- 経路読込、座標投影、追従、停止属性、回避・再経路の基本構造がある。回避復帰時に停止属性のある点を飛ばさない配慮がある。
- GNSS/LIO融合には外れ値・入力異常対策、品質による減速、欠測復帰のテストがある。
- UIからの自律指令経路とYPSpur起動設定は整備されている。ただし、起動プリセットによる構成差は残る。

## P0-1 停止距離モデルと下位設定が不一致

根拠: `src/robot_navigator/params/default.yaml` の max_acc_v は1.0 m/s²。`src/ypspur_ros2/config/default.yaml` の acceleration_max.linear は0.3 m/s²。`robot_navigator_node.py` の compute_time_optimal_cmd_vel内では、max_acc_vを減速度として障害物停止距離を計算する。

1.0 m/sからの理想制動距離は、上位の仮定では0.50 m、下位設定を減速度に用いると1.67 m。差は約1.17 mで、遅延や誤差をまだ含まない。上位には別途安全余裕があるが、この不一致自体は解消しない。衝突や実際の停止距離を観測したという意味ではない。

必要: 指令生成・障害物判定・ドライバで速度と加減速の契約を統一し、停止点への接近でも残距離に応じて早期減速する。通常停止と保護停止を区別し、実効減速度・遅延を明示する。

合格条件: 設定不一致を起動時に拒否。0.1/0.5/1.0 m/s、遅延あり、旋回中の停止をシミュレーションし、所定境界を越えない。後日必要な実測は別作業とする。

## P0-2 回避幅の上限を超える目標を生成する

根拠: `src/route_follower/route_follower/follower_core.py` の _start_avoidance_sequence / pick_offset。許可幅と観測幅がともに0.10 mでも、最低回避幅0.35 mを優先して横方向0.35 mの目標を生成した。今回再現済み。

必要: 最低必要幅を確保できない場合は回避不可として停止する。許可領域・車体の通過領域・後方を含む軌跡で判定する。現在の後退側にずらしたL字目標は、後方や旋回中の通過領域を保証しない。

合格条件: 許可幅0、0.10、0.34、0.35 mの境界試験で上限を越えない。路側帯・道路端・歩行者側に抜ける候補を生成しない。回避不能時は停止を維持する。

## P0-3 到達状態と実停止が連動していない

根拠: followerの到達半径0.6 mに対しnavigatorの位置許容は0.5 m。停止点の0.55 m手前でWAITING_STOPになり、最終点ならFINISHEDになることを再現した。速度ゼロの確認はしていない。これは個々の停止位置が必ず規則違反という意味ではなく、状態表示から実停止を保証できないという問題。

`route_follower_node.py` の _handle_target_publish は目標Noneなら送信しない。navigatorはfollower_stateを購読せず、以前のactive_targetを保持する。FINISHEDやERRORで目標送信を止めるだけでは停止契約にならない。目標・ミッションのheartbeat監視もない。下位cmd_velタイムアウトは、navigatorが古い目標へ新しい指令を送り続ける場合を止められない。

必要: run/pause/stop/finished/errorを下位に伝え、速度ゼロ確認後に停止完了へ遷移する。ミッション途絶・中断・終了時は明示的に目標解除とゼロ指令。manual_start=FalseはRUNNINGの停止操作にはならないため、再開操作と停止操作を分離する。

合格条件: follower停止・ハング・ERROR・FINISHED・UI中断の各ケースで出力ゼロ。停止完了前の再開要求を拒否し、古い要求を次の停止へ持ち越さない。再開はその停止状態に対する新しい操作でのみ受理する。

## P0-4 観測不能と障害物なしが混同される

根拠: obstacle_monitorの _is_front_blocked は空点群または5点未満で「非閉塞・距離無限大」を返す。空点群ケースを再現した。navigatorの on_hint は非有限距離をNoneに変換し、障害物距離制約を解除する。メッセージが新しくても有効な観測とは限らない。

また、navigatorの障害物停止は直進速度をゼロにしても、向き誤差が残ると旋回指令を維持する。車体が旋回で掃く領域の安全確認は別に必要。

必要: 観測正常・有効な空間・観測不能を分離し、センサ仕様上の「返りなし」と破損・全無効データを区別する。タイムスタンプ、有限値、有効率を監視し、不明時の停止を全起動経路で統一する。

合格条件: 全NaN、壊れた値、古い時刻、途絶、少数点、正常な返りなしを個別試験。障害物至近では直進・旋回とも安全側の出力となり、鮮度だけで異常が解除されない。

## P1-1 大会の停止線・道路端・ゴールを表現できない

根拠: Waypointの停止属性はline_stopとsignal_stopのboolのみ。道路端と停止線の区別、境界線の向き、許可停止領域、車体全体のゴール通過条件はない。距離半径での到達を公式の停止判定に代用できない。

必要: stop_line / road_edge / finishの種類と境界形状、車体領域を含む停止判定、減速開始点を経路に持たせる。停止線→道路端の順序を明示し、停止完了後の安全確認・再開をUIに表示する。B不実施時はオペレータの安全確認による再開経路を採る。

合格条件: 公式の位置範囲の内外、斜め姿勢、位置誤差込みで判定を試験。ゴールは車体全体が越える前には完了せず、越えた後に自律停止する。これはHW変更ではなくソフトウェアの幾何判定の不足。

## P1-2 待機列と狭路に応じた回避禁止がない

根拠: followerは滞留を検出すると左右開放幅を使って回避するが、待機列・追い越し禁止・車道進入禁止の領域種別を持たない。停止前の滞留にも回避判定が働く。左右幅をゼロにする設定で抑制できる場合はあるが、経路全体での強制や検証はない。

必要: queue / no_overtake / no_lateral_escape / no_entry等の領域制約を回避と再経路の双方に適用する。前が空いた時は列に沿って進む。ホテル狭路で通れない場合は自律停止・運搬待ち・位置再確認・明示再開の状態を持たせる。

合格条件: 列が長時間停止しても横抜けしない。空きができれば前進し、境界外への再経路を拒否する。運搬後に古い位置・古い目標のまま自動再開しない。

## P1-3 大会モードと起動設定の統一が必要

根拠: drive_mode_coreには手動切替と自動復帰があり、操縦を禁止する専用モードはない。allow_auto_resume=Falseは手動への切替禁止ではない。共通実機bringupではjoy/manual_teleopが起動対象となる。競技中の操縦コントローラ操作不能化をこの設定だけで満たせるとは判断できない。

UIの「実機（融合）自律」は共通構成、「実機」は個別起動構成。共通実機ではobstacle_timeout_sec=1だが、navigatorの単体既定値は0。融合による指令制限も構成によって異なる。

必要: experiment / confirmation / record / finalのモードを定義する。競技モードでは操縦入力とデバッグ用GO・疑似障害物入力をロックし、認められた再開操作を独立させる。UIとCLIで同じ設定検証・制御経路を使い、有効設定を記録する。

合格条件: 競技モードでスティック・切替操作・UI疑似入力が運動指令へ影響しない。UI/CLIとも同じタイムアウト・速度制限が適用され、競技モードへの不適切な構成を拒否する。ソフトウェア停止を非常停止適合と取り違えない。

## P1-4 自己位置の不確かさに対する停止基準が不足

根拠: fusion_core.diagnosticsは位置標準偏差が1 m以上でも速度上限0.25 m/sを返す。データ途絶への停止はあるが、大きな位置不確かさに対する絶対的な停止基準はこの分岐にない。

必要: 通行幅と境界までの距離に対し、位置・方位の不確かさを加味した走行可否判定。測位復帰直後の飛び・原点不整合・運搬後の再局在を停止解除条件に含める。

合格条件: 更新が続いていても不確かさが許容領域を越えれば停止。復帰時に境界を飛び越えた到達扱いや急な操舵を発生させない。

## P1-5 本番経路の承認と大会シナリオ試験が不足

根拠: tsukuba2026_digital_twinの1,142点はREADMEで「現地確認済みの本番経路ではない」と明記。これは同梱検証経路であり、現在の実機セッションがこの経路を選択しているという意味ではない。hardware_coreが生成するroute_review_requiredは、生成とテスト以外で起動拒否に使われていない。

必要: 経路ごとの停止点・道路端・禁止領域・列待機のレビュー、座標系と版の固定、未承認経路の競技起動拒否。公開地図による全周試験と大会条件への適合試験を区別する。

合格条件: 未承認、停止属性欠落、投影不一致を起動時に拒否。停止点、列待機、狭路、測位異常、認識途絶、ゴールまでを含むオフライン統合試験で、全指令と状態遷移を記録する。その後の実環境検証は別途行う。

## P2 運用時間・記録・選択課題

全体の制限時間、開始・20 m通過、確認区間の停滞、列が空いてからの停滞を判別するミッション監視を追加する。公式がタイマーのソフトウェア実装を義務付けているという意味ではなく、失敗条件への気付きと事後検証のための改善。既存のログ・bag機能を利用し、ルート版、実効パラメータ、状態遷移、停止理由、再開操作を一緒に残す。

A: 既存の地図・経路の利用可否と作成由来を区別する仕組みが必要。単に未知障害物を回避できるだけでは達成を示せない。

B: 信号認識の基盤はあるが、信号GOだけでは交差点内の安全確認を満たさない。信号判定の鮮度、有効な停止状態、車両との競合確認を統合した横断許可が必要。必須課題の完走を優先する間はB不実施として扱う。

D1/D2/E: 宅配先認識・訪問計画、集配タスクの状態管理、最初にすれ違ったロボット番号の認識・報告について、大会課題として完成した実装を調査範囲で確認できなかった。D2の機構は本評価の対象外。Cは2026年不実施なので優先実装しない。

## 着手順と判定ゲート

1. P0を修正し、今回の再現ケースを回帰テスト化する。停止距離設定・回避幅・指令失効・観測不能・旋回時保護を先に確定。
2. P1-1〜3を実装し、大会モードと経路の意味を揃える。停止確認→再開の契約をUIからドライバまで統一。
3. P1-4〜5を満たす位置品質判定、経路承認、競技シナリオ試験を整える。
4. 全周の状態遷移・停止条件・時間条件を検証し、その結果を踏まえて実機確認を別途計画する。今回は移動不要の評価まで。
