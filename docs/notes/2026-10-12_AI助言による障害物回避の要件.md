# AI助言による障害物回避の要件

状態: 検討中
作成日: 2026-10-12
対象コミット: afcbd4e
決着期限: 2026-10-26

停止後にAIエージェント（`claude -p` 相当のCLI）へ回避方向とオフセットを問い合わせ、
その助言を既存のL字回避へ入力する。R1〜R7は実装済みで、既定は無効のまま従来動作となる。
残るのはR8の評価シナリオと、実際のAIエージェントを使った妥当性確認である。

---

## 背景

現行の障害物回避は、obstacle_monitorがtopURGの`/scan`だけから前方閉塞と左右オフセットを
求め、route_followerが滞留15秒の継続で左右どちらかへL字のサブゴールを生成する。
左右の選択は「オフセットが小さい側、同値なら左」であり、障害物の種類も静止・移動の別も
判断に入らない。回避幅は採取値か手修正に依存する。

これまでの走行で停止に至る代表例は、運営が設置した緑のロードコーン、車止めのようなポール、
同じ方向に走行しているロボット、反対方向に走行しているロボット、草、人である。
静止物はすぐ再開したいが、人やロボットのような移動障害は少し待って状況の改善を待つ方が
良い。現行実装はこの区別を持たない。

## 調査・分析

### 判断点の所在

左右の選択とオフセット決定は`route_follower`の回避サブゴール生成の一点に集約されている。
助言の差し込み先はここに限定でき、既存の状態遷移を組み替える必要はない。

### センサ取付

本件で前提とする取付値は次のとおりである。topURGは床上0.25 mで、MID-360より下にある。

| 対象 | base_link相対xyz [m] | 床上高さ [m] | 姿勢 |
| --- | --- | --- | --- |
| base_link（車軸中心） | — | 0.148 | — |
| topURG（`laser`） | 0.075, 0, 0.10 | 0.25 | 水平 |
| MID-360（`mid360_frame`） | 0, 0, 0.414 | 0.562 | roll -0.6°、pitch 26.9°（前下がり） |

MID-360の値は`src/icart_bringup/params/hardware.yaml`にある2026-09-22の点群計測値である。
`src/icart_bringup/launch/hardware.launch.py`が`base_link`からの静的TFをこの値で配信する。
前下がり取付は`hardware_parts/mid360_mount_25deg/`のマウント部品に対応し、
CADの設計角は25°、計測値は26.9°である。
`src/FAST_LIO/config/mid360.yaml`の`extrinsic_T/R`はLiDAR→IMUの工場較正であり、
車体への取付傾斜を含めない。`livox_ros_driver2`の設定も`pitch: 0.0`でドライバ側補正を使わない。

topURGの値は`hardware.yaml`では`z=0.49`（床上0.638 m）となっているが、これはMID-360より
高い位置を指し、実機の取付と一致しない。本件では`obstacle_route_sim/models/robot/model.sdf`
が持つ床上0.25 mを採用する。`hardware.yaml`の修正は本件の範囲外とし、実測して確定する。

同モデルはMID-360を床上1.005 mの水平取付とし、カメラを持たない。この2点は実機と異なるため、
模擬環境での確認に使う前に更新を要する。

### 水平スライスの成立条件

MID-360の仰角範囲は-7°〜+52°である。前下がり26.9°により車体基準のビーム範囲は
-33.9°〜+25.1°となり、センサ高0.562 mでは距離dにおける観測可能な高さ帯が
`0.562 - 0.672d` 〜 `0.562 + 0.468d` [m] になる。最下段ビームの地面交点は0.84 mである。

| 前方距離 [m] | 観測できる高さ帯 [m] |
| --- | --- |
| 0.75 | 0.06 〜 0.91 |
| 1.0 | 地面 〜 1.03 |
| 1.5 | 地面 〜 1.26 |
| 3.0 | 地面 〜 1.97 |

水平取付ではこの高さ帯が近傍に存在せず、停止判定が起きる0.75〜1.5 mで低い層の点が
得られない。前下がり26.9°であれば近傍でも低い層を観測でき、水平スライスが成立する。

層はtopURGの0.25 mとMID-360設置高0.562 mの間をほぼ等間隔に割る。

| 層 | 床上高さ [m] | 狙う対象 | 観測開始距離 [m] |
| --- | --- | --- | --- |
| 既存層 | 0.25（topURG） | 現行の前方閉塞判定 | — |
| 下層 | 0.35 | 車止めの下部、コーンの底部、低い段差 | 0.32 |
| 上層 | 0.50 | コーン本体、草、ポール、ロボットの車体 | 0.09 |

人の胴体高さ1.1〜1.2 mは1.4 m以遠でしか観測できない。近傍での人とロボットの識別は
カメラ画像の役割とする。

MID-360は非回転の疎なスキャンであり、厚さ数cmの層に単一フレームで乗る点は少ない。
スライスは複数フレームの累積を要する。問い合わせは停止中に行うため自己運動補正の負担は軽い。

### AIをCLIで呼ぶことの制約

推論は機上PCで`claude -p`相当のCLIを起動して行う。他のノードと同一PCで動くため、
プロセス起動がFAST-LIOやYOLOと計算資源を争う。CLIの起動から応答までは数秒から十数秒で、
制御周期50 msとは別の時間軸になる。推論自体はクラウドAPIへの往復であり、
機上実行でも回線品質による失敗は残る。

現行の滞留検知は15秒継続で回避を開始する。ここへCLIの待ちを直列に足すと1回の障害物で
25〜30秒停止する。問い合わせの開始条件を「実速度ほぼゼロかつ前方閉塞の多数決成立」に
置くと、滞留15秒の内側にCLIの遅延を隠せる。

この先行発火には、低速の先行ロボットへ追い付いて止まる動作を繰り返す場合に
呼び出しが嵩む弱点がある。停止持続ゲート、移動量クールダウン、助言キャッシュ、
呼び出し予算の4つで上界を与える。

### 前方ロボットへの追従

robot_navigatorは障害物ヒント距離からブレーキ距離を求めて減速・停止する。
route_followerが回避を発動しなければ、前車が動けば自然に追い付いていく。
同方向に走行するロボットへの追従に専用の制御は要らず、必要なのは
「回避を発動しない状態」だけである。robot_navigatorの改修は本件に含めない。

現行の`stop_dist_m`は0.75 mで、`docs/走行システムの機能と制約.md`が示す1 m/s時の
停止距離概算1.083 mより小さい。実際には前方余裕距離による減速が先に効くが、
追従時の実効車間は模擬走行で確認する。

## 提案

### 要件

| ID | 要件 |
| --- | --- |
| R1 | 実速度ほぼゼロかつ前方閉塞の多数決成立が3秒継続した時点でAIへ問い合わせる。滞留検知の時点で助言があれば採用し、無ければ待機上限後に従来回避へ移る |
| R1-a | 停止持続ゲート、移動量および時間のクールダウン、同一waypointの助言キャッシュ、分あたりと走行全体の呼び出し予算で呼び出し回数に上界を与える。パラメータ1つで従来動作へ戻せる |
| R2 | 助言は行動種別（回避・待機）、左右、オフセット、待機時間、移動の有無、確信度を持つ。障害物の種類と根拠文は情報項目とし、制御の分岐に使わない |
| R3 | MID-360の点群を`base_link`基準で床上0.35 mと0.50 mの2層にスライスし、層ごとの空き幅と可視化画像を出力する。前方閉塞判定には使わない |
| R4 | AIへの入力は3層の点群画像、フロントカメラの静止画、および寸法の構造化テキストとする |
| R5 | CLIは非同期で起動し、タイムアウトでプロセスグループ単位に終了する。出力はJSON単一オブジェクトに限定し、パース失敗・スキーマ違反・範囲外値は従来回避へ退避する |
| R6 | 待機状態を追加する。待機中に前方閉塞の多数決が崩れたら即復帰する。待機時間は助言値を使い、既定10秒、上限30秒とする |
| R7 | 採用オフセットは、採取幅・実測空き幅・大域上限の最小値でクランプした範囲内に限る |
| R8 | 模擬環境にコーン、人、同方向および対向のロボットのシナリオを用意し、AI使用の有無を同条件で比較する。追従時の実効車間も確認する |

行動種別から「避けずに進む」を外す。草もコーンと同じ静止障害物として回避する。
障害物検知を意図的に無視する経路を作らない。

横断歩道上で停止せず回避する特例は本件に含めない。経路データに区間属性が無く、
走行しながらの回避は現行の回避起動条件と両立しないため、別に扱う。

### 構成

```text
/mid360/livox/lidar/points → [層スライス] → 層ごとの空き幅・可視化画像
/scan                      → [obstacle_monitor] → /obstacle_avoidance_hint （無改修）
/usb_cam/image_raw ─┐
層の可視化画像 ─────┴→ [助言ノード] ←action→ route_follower
```

助言ノードとroute_followerの間はROS 2 actionとする。タイムアウト時のgoalキャンセルから
CLIプロセスの終了までを一つの契約で表せる。

### AI入力画像

既存の`sensor_viewer`は目視用として現行仕様を保ち、AI入力用の画像を別に生成する。
実距離に比例した画素配置、下端中心をセンサ位置とする原点、白背景と赤点という
現行の描画方針は保つ。AI入力用には以下を加える。

- 1 mごとのグリッドと距離の数値ラベル
- 車体矩形（半幅0.3 m）と進行方向
- 表示範囲を前方0〜4 m、左右±2 mへ寄せ、縮小を掛けない
- 3層を同一スケール・同一原点で並べ、各層の定義をラベル表示する

寸法は構造化テキストでも渡すため、制御に使う数値が画像の読み取り精度に依存しない。

## 残作業

- R8 の評価シナリオ（コーン、人、同方向および対向のロボット）を模擬環境へ用意し、
  AI 使用の有無を同条件で比較する。追従時の実効車間も測る。
- 実際の `claude -p` を使った応答時間、応答形式の安定性、判断の妥当性の確認。
- 共通起動（`icart_bringup`）へ `lidar_layer_slicer` と `avoidance_advisor` を組み込むか、
  個別 launch のままにするかの判断。現状は個別 launch のみで、共通起動には入れていない。
- 記録済み bag を使った層の高さの見直し（点数と観測距離の集計）。

## 未確認事項

- `hardware.yaml`のtopURG取付値は実機と一致しない。実測による確定は本件の範囲外である。
- `claude -p`の実機PCでの応答時間を測っていない。問い合わせの先行発火が滞留15秒の内側に
  収まるかは未確認である。
- CLI起動時のCPU・メモリ競合がFAST-LIOと制御周期へ与える影響を測っていない。
- AIが代表6例を画像から正しく分類できるかを確認していない。画像仕様とプロンプトは
  模擬環境での確認後に決まる。
- 層の高さ0.35 mと0.50 m、層の厚さは幾何計算と対象物の寸法からの選定であり、
  実機の点群で妥当性を確認していない。記録済み bag では、前下がり26.9°の取付で
  両層に点が乗ることまでを確認した。
- 待機の既定10秒・上限30秒は、上限を現行の再経路待機30秒と揃えた設計値であり、
  実走での妥当性は未確認である。
- 模擬環境のカメラ画像が実機のC920の画質・画角をどこまで代表するか不明である。
- `camera_optical_frame`の静的TFは配信されていない。画像をそのまま渡す範囲では
  問題にならないが、点群と画像を対応付ける場合は追加を要する。
- 外部APIを使う判断支援が大会規則上どう扱われるかを確認していない。
