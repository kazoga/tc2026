# i-Cart mini 共通起動 設計・運用

## 1. 目的・対象

実機と地形デジタルツインで、同じGNSS/LIO融合と既存robot_console PyQt5 UIを使う。
robot_console_gui_architecture_design.mdの起動profile・Snapshot分担と、
gnss_lio_fusion詳細設計書に合わせる。実車の接続先や校正値を自動決定する機能ではない。

## 2. 要求と範囲

同じsession.yamlとenvironment切替で原点・経路・走行処理を共有する。
地形生成はobstacle_route_sim、測位はgnss_lio_fusion、操作表示はrobot_consoleに置く。
このパッケージは起動と入力設定の検査だけを担当する。

## 3. 構成

simulationではGazebo、bridge、模擬URG/GNSS、LiDAR/IMU adapterを起動する。
realでは模擬センサを起動せず、hardware_launchで指定した実機起動構成を取り込む。
空ならドライバを別起動する。FAST-LIO、融合、地理座標変換、経路管理、追従、
障害物監視、navigator、cmd muxは両環境で共通とする。

## 4. ファイル配置

| 配置 | 責務 |
| --- | --- |
| icart_bringup/session_core.py | 設定生成・相対パス解決・入力検査 |
| launch/bringup.launch.py | 環境切替・共通起動・終了連携 |
| docs/ | 本パッケージの運用と検証 |
| tests/ | ROS非依存の設定・異常系検査 |

prepare_sessionはsession_world.sdfも生成し、物理刻みを1 msにする。原本は変更しない。
既知の車輪の関節軸を等価な局所-Z表現へ変換し、未指定の駆動上限を2 Nm・20 rad/s、
旋回速度を±1.2 rad/s・旋回加速度を±1 rad/s²とする。既存の明示上限は保持する。
これらは発振比較用の有限制約であり、実機モータの実測値ではない。
地形接触計算と駆動の修正であり、センサノイズを弱める変更ではない。
1 msでも物理妥当性を保証しない。真値の旋回速度が2 rad/sを超えた区間を別途検査する。
prepare_sessionの生成物をソースやGitへ追加しない。地図を複製せず、参照する。
実機と模擬の両方を統合する責務なので、シミュレータのtoolsに起動本体を置かない。

## 5. 外部インタフェース

| 入出力 | 内容 |
| --- | --- |
| /scan | URG LaserScan。simulationは270度・1080点・最大30 m |
| /lio/odometry | FAST-LIOのOdometry。真値を代替入力にしない |
| /rtk_gps/fix、/rtk_gps/rtk_status | simulationのGNSS。realは既存private名からremap |
| /localization/pose_enu | 融合した車軸位置・yaw。唯一の配信元は融合ノード |
| /localization/pose_llh | UIの地図用にroute_geo_projectorが変換 |
| /fusion/status | 方位σ、baseline、モード、棄却数 |
| /manual_start | 既存UIからの走行開始入力 |
| /cmd_vel/autonomous → /cmd_vel/fusion_limited → /cmd_vel | navigator→融合減速→mux |
| /ypspur_ros/odom | 実機の車輪またはGazebo駆動odom。navigatorへ入力 |

LIO異常時は車輪相対運動へ退避し、GPS_WHEEL/WHEEL_PRIORITYを表示する。
自己位置の真値配信はしない。真値は模擬GNSSと評価器のみに使う。
QoSは各責務パッケージの既存仕様を保持する。

## 6. 設定

session.yaml内のパスはsession.yamlのディレクトリから解決する。

| キー | 既定値・用途 |
| --- | --- |
| projection_params | 必須。原点とmap yawを持つ共通ROS YAML |
| route_config、csv_base_dir | 必須。route_plannerの設定と経路CSV所在 |
| trial_sdf | 任意。prepare_sessionが生成する1 ms刻みのsession_world.sdf |
| trial_directory | simulationで必須。IMU追加済みtrial.sdf、world.json、trial.json |
| start_label、goal_label | 開始0、終点は必須。prepare_sessionで全区間から生成 |
| physics_engine | gz-physics-dartsim-plugin。エンジン差分検証用 |
| noise_profile、noise_seed | conservative、1。実測校正済みという意味ではない |
| building_gnss | true。建物近傍のFLOAT・biasを有効にする |
| hardware_launch | real専用。既存ドライバ起動ファイル。空なら外部起動 |
| fusion_params | 任意。取付方位補正などの融合ROS YAML |
| fastlio_config | real専用。空ならfast_lioのmid360.yaml |
| gnss_namespace | realの既定/rtk_gps/rtk_gps_um982_node |
| simulation_domain_id、real_domain_id | 86、0。親プロセスのDDS domainと照合する |

任意のFAST-LIO設定を入れる場合、センサの型・時刻単位・外部パラメータを実機と一致させる。
実機のURG IP、Livox接続先、UM982ポート、YP-Spur設定はhardware_launch側で管理する。
既存ドライバを二重起動しない。融合の角度取付補正はgnss_heading_offset_degと
lio_yaw_offset_degで指定する。両者の共通方位biasは二つの観測だけで自動校正できない。
共通起動は、指定済みの前master・後slave配置に合わせgnss_heading_offset_deg=180を使う。
模擬GNSSもANT1→ANT2の生方位を出す。受信機側で角度補正している場合はfusion_paramsで
0等へ上書きし、二重補正しない。単体fusion.launch.pyの既定補正は0のままである。
根拠は[Unicore N4 Command Manual 1.3 HEADING Configuration](https://en.unicorecomm.com/uploads/file/Unicore%20Reference%20Commands%20Manual%20For%20N4%20High%20Precision%20Products_V2_EN_R1.13.pdf)
のmaster→slave、真北時計回りの定義である。実機で向きを既知の方向へ合わせて確認する。

## 7. 状態・座標・時刻

投影原点とroute CSVは同一sessionを使う。simulationはROS clock、realは実時間を使う。
融合ENU yawはmapの+xから反時計回り、受信機headingは真北から時計回りであり、
UIは両方の基準を明示する。表示σは推定不確かさであって真値誤差ではない。

## 8. 操作フロー

1. 地形を生成し、prepare_fastlio_trial.pyでIMUを追加する。
2. prepare_sessionでsession.yamlを準備する。
3. UIと走行系を同じDDS domainで起動する。
4. UIの起動設定で「デジタルツイン／自律走行」または「実機（融合）／自律走行」を選ぶ。
5. プリセットを適用し、起動設定タブのi-Cart融合profileを選ぶ。
   ノード設定編集パネルのconfig欄へsession.yamlを指定して全起動する。
6. 地図・RTK・融合方位・scanを確認し、既存manual_start操作で走行を開始する。
7. UIから全停止後、環境を切り替える。起動中のモード名変更だけでは環境は変わらない。

上記はUI単独起動からの操作である。下記のstart_ui:=trueによるCLI一括起動では、
走行スタックは既に起動しているため、UIで起動profileを再度起動せずmanual_startだけを使う。
終了は起動元のCLIで行う。UIから全停止する運用にはUI単独起動の手順を使う。

旧「シミュレーション」と「机上確認」の簡易模擬機能は残す。
融合プリセットと旧の個別走行profileを同時に起動しない。
デジタルツインの手動走行プリセットは空であり、今回の対象は自律走行である。

## 9. 主要判定

sessionの必須入力をプロセス起動前に検査する。environment以外の値を許容しない。
simulationでhardware_launchは使用しない。実機との混信を防ぐため、DDS domainが
設定と一致しない場合は起動を拒否する。親UIのdomainを子launchから変更しない。

## 10. QoS・並行性

各ノードの購読・発行QoSを継承する。UIは揮発的な表示Snapshotと既存鮮度監視を使う。
navigatorの受信期限は両環境とも1秒とし、実機は単調時計、simulationはROS時計で測る。
物理計算の低速化やpauseのwall時間を欠測に数えない。融合もROS観測時刻で
入力の古さを判定し、全運動入力途絶では指令をゼロにする。URG停止は解除しない。
UIのRTK購読は模擬の公開名と既存実機private名に対応する。同一domainで両系を起動しない。

## 11. 起動と終了

```bash
source install/setup.bash
# 必要なら、導入済みGazeboローカルruntimeも有効化する。
export ROS_DOMAIN_ID=86
export ROS_AUTOMATIC_DISCOVERY_RANGE=LOCALHOST
ros2 run icart_bringup prepare_session --trial <IMU追加済み地形> --output <新規sessionディレクトリ>
ros2 launch icart_bringup bringup.launch.py session:=<sessionディレクトリ>/session.yaml environment:=simulation start_ui:=true
```

DDS domainを自動設定する入口も使用できる。実機と模擬の切替時には全停止してから再起動する。

```bash
ros2 run icart_bringup run_session --session <sessionディレクトリ>/session.yaml --environment simulation --start-ui
ros2 run icart_bringup run_session --session <sessionディレクトリ>/session.yaml --environment real --start-ui
```

run_sessionは設定検査後にdomainを設定してexecする。realのdiscovery設定は親シェルを保持する。
CLI同時起動のUIには初期環境名も渡す。UI単独起動では前述のdomain設定を行う。
実機では全停止後、実機domainのシェルからenvironment:=realで直接launchしてもよい。
ソフトウェア切替を実車で検証済みとは扱わない。初期状態はmanual_start待ちである。初回は良好FIX・方位・LIOを必要とし、
FLOATのみで起動した場合はUIに「初期FIX待ち」を表示する。
主要子プロセス終了時は共通launch全体を終了する。UI profileの停止も子を終了させる。
非常停止・手動介入は既存drive_mode_managerのJoyインタフェースを使う。
実機hardware_launchにJoy/manual teleopを含める場合も、cmd muxは本launchの一つだけを使う。

## 12. エラー・ログ

ファイル不足やdomain不一致はValueErrorで起動前に検出する。ノード出力は既存UIログへ集約する。
長時間の入力欠落は各ノードのwatchdogが扱う。UIの数値が残っていてもfreshnessを確認する。

## 13. UI

GPS/PoseカードにGNSS heading、融合yaw、推定方位σ、融合mode、推定基準距離を表示する。
地図・waypoint・manual_startの既存操作を共有し、別の走行UIは作らない。
iPhone向け成果物は会話内画像と本文で提供する。localhostやPCパスを共有URLとしない。

## 14. 依存・ビルド

ament_pythonで管理する。依存パッケージはpackage.xml、Python依存はsetup.pyに記述する。
PyYAMLは既存ワークスペース依存を利用する。通常installとsymlink-installの両方を確認する。

## 15. 試験・受入条件

設定の相対パス・未設定値・環境差分、UI Snapshotと異常JSON、起動profileをpytestで確認する。
隔離GazeboでUI経由開始、位置・方位・地図・scanの受信、単一pose配信元、終了を確認する。
実機の配線・接続・方位校正・実走は別途確認事項とする。

## 16. 互換性

旧profileは削除しない。融合profile追加時だけ共通構成を使用する。
GPS単独ENUを/gnss/pose_enuへ分離し、融合出力と競合させない。

## 17. 残事項

実車固有のhardware_launch指定、時刻同期と取付補正、LIO内部退化・車輪スリップ判定の追加が残る。
環境切替は試験手段を共有する機能であり、実環境での完走認定ではない。

### ウェイポイント保存の統一（2026-09-14）

route_planner README「CSV仕様」と詳細設計書8.2を保存仕様の根拠とする。
旧prepare_sessionは試験ディレクトリのroute.csvを直接参照し、LLH/ENU併記も引き継いでいた。
新prepare_sessionはroute_storage_coreを介し、session配下の
routes/fixed/waypoints.csvとroutes/route_config.yamlを保存する。
csv_base_dirはroutes、start_label/goal_labelは実際のCSVの先頭・末尾labelから取得する。
LLHが揃う行は既存reader同様にLLHを正本とし、不完全な旧行はENUから変換する。
ENUからの変換は共通geo_coreで原点高度とmap回転を反映する。
高度列は規定どおり空欄とし、走行用ENUを同じCSVに重複保存しない。
CSVの順序、label、左右回避幅、停止・スキップ属性を維持する。

旧sessionと過去ログは互換のため保持する。新規出力先へprepare_sessionを再実行して移行する。
保存形式の検査では既存route_planner readerによる座標・方位の往復、回転原点、属性保持を
確認する。全周1,142点の検証用経路はroute_planner/routes/tsukuba2026_digital_twinへ配置する。
この保存形式変更は実コースの測量精度や停止属性の妥当性を新たに保証するものではない。
