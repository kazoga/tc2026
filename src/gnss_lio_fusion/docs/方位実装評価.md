# 方位推定・共通UI連接の実装評価

## 1. 対象と判定方針

2026-09-13に、詳細設計書・実装評価の第一段階へ方位異常処理と共通起動を追加した。
位置が一致することだけで方位を合格とせず、同一時刻の真値yawとの差を±180度へ折り返して
RMSE・95パーセンタイル・最大絶対値を評価する。真値を融合入力には使わない。
全周の記録再生と、Gazeboを実際に制御した閉ループ試験を区別する。

## 2. 問題と修正

| 問題 | 修正・検証観点 |
| --- | --- |
| 位置残差がyaw更新に混入する | 位置2次元更新と円周上の方位観測を分離する |
| 位置観測棄却により良好な方位も失う | 方位品質を別評価し、位置ゲートより先に更新する |
| ±180度折返し・突然の反転 | 最短角度残差、時間方向の角速度ゲート、45度innovationゲート |
| LIO大ジャンプ後、45度ゲートが復帰を妨げる | 既知のLIO異常時だけ良好FIXの2秒連続性で再取得する |
| 再取得中の品質欠落 | 再取得履歴をリセットし、次回の時刻差計算を保護する |
| FLOAT期間に位置補正が完全に失われる | 品質に応じた低重みと残差に応じた分散拡大で弱い補正を残す |
| LIO途絶・車輪との不整合 | 同時刻の相対運動を照合し、車輪odomへ連続的に退避する |
| 全運動入力途絶を最新poseと誤認する | 新しい運動がない場合はpose stampを更新せず、既存watchdogで停止する |
| 前master・後slaveの生方位が後ろを向く | 共通起動で180度補正し、模擬GNSSもANT1→ANT2を再現する |

補正速度は最大0.12 rad/sとし、再取得による瞬時の方位反転を避ける。
受信機の方位標準偏差が0・非有限の場合は未知として扱う。FIXであるだけでは信用しない。
baselineは高品質時に緩やかに追従し、変化時は信頼度を下げ、安定した新距離を再取得する。
baselineの一貫性は共通の方位biasや共通モード位置誤差を検出できる保証ではない。

車輪退避はMotionGuardに分離した。絶対odom原点を一致させず、相対運動を積分する。
差分の許容値は並進0.08+0.6dt m、方位0.08+0.3dt rad、復帰待機1秒である。
物理上限は2dt+0.15 m/rad、最大入力間隔1.5秒である。これらは実測校正前の値である。
車輪も滑るため、退避中は最高0.4 m/sとしてGPS_WHEEL/WHEEL_PRIORITYを表示する。
LIOが初期化前から全く届かない状態の自動発進は対象外である。
障害物停止を解除しない。完走優先でも全入力欠落を架空の移動で補わない。

## 3. 全周記録の再生

元データはlog/codex/fusion_trial/full_route、比較は
log/codex/heading_trial/replay_finalに保存した。同じ入力記録へ方位・位置更新を適用する。
最終FusionFilterコアで再計算したが、旧ログに車輪がなくMotionGuardを通さない。
最終版で全周を再走した結果ではない。

| 指標 | 従来融合 | 方位分離・弱FLOAT補正 |
| --- | ---: | ---: |
| 方位RMSE [deg] | 0.538 | 0.488 |
| 方位最大絶対誤差 [deg] | 4.327 | 4.380 |
| 位置RMSE [m] | 1.619 | 1.434 |
| 位置最大誤差 [m] | 9.766 | 8.591 |

従来融合から平均は改善したが、方位最大値は僅かに悪化した。

この記録では位置精度がGNSS単独より常に優れるわけではない。走行経路を再最適化した値ではない。
旧ログに分散と方位標準偏差がなく、51,047件を当時のFIX/FLOAT模擬設定から補った。
比較有効50,187件、共通時刻外など858件を除外した。再現性の制約として残す。

## 4. 故障注入と閉ループ試験

### 4.1 初回の短い方位反転

log/codex/heading_trial/transition_fault_run: 70 waypoint、約133.4 m。
conservative LiDAR/IMU、建物近傍FLOAT、baseline 500→520 mm、180度反転0.3秒（wall clock）を使用した。
全waypointを通過しgoal判定に到達した。車体接触0、真値走行時間約220.5秒であった。

| 指標 | GNSS | FAST-LIO | 融合 |
| --- | ---: | ---: | ---: |
| 方位RMSE [deg] | 6.590 | 1.714 | 0.437 |
| 方位最大絶対誤差 [deg] | 179.783 | 2.676 | 1.708 |
| 位置RMSE [m] | 1.003 | 11.655 | 0.966 |

融合位置最大4.109 m、経路横ずれ最大1.467 m、±1 m以内92.05%であり、
完走と全区間の狭い通路内維持は同義ではない。baseline推定は519.882 mmに再取得した。

### 4.2 別seed・5秒反転による追加試験

方位故障の時刻・継続時間はwall clockであり、低速シミュレーションの5秒間とは異なる。
seed=2でのUI連接試験では、真値車体が短時間で反転する物理挙動とLIOジャンプを観測した。
最初は大方位差ゲートが復帰を妨げたため、既知LIO異常後の再取得を追加した。
その再生では方位RMSEが98.8→40.6度となり終盤に復帰したが、良好な走行とは判定しない。
さらに車輪退避を追加し、入力途絶・再接続・原点差・二重積分の単体試験を追加した。
物理挙動の異常で中断した試験を完走として数えない。

DARTの1 ms化だけでは真値角速度27.8 rad/sの異常を解消できなかった。
Bullet Featherstoneへの単純切替では、車輪odomに0.3 m/sが出ても車体がほぼ進まなかった。
従ってエンジン切替だけを改善策として採用しない。車輪関節と駆動制約を別途比較した。

### 4.3 ROS入力途絶

tools/check_fusion_dropout.pyは隔離domain=87で実ROSノードを起動する期限付き試験である。
LIOのみ途絶した間に車輪でpose・走行指令が継続し、両運動入力途絶後にはゼロ指令となった。
pose受信36件、車輪退避26件、3条件すべて合格した。Gazebo走行試験とは別である。

### 4.4 物理制約追加後の900秒試験と受信監視

console_actuated_seed2では異常旋回がなく、真値最大角速度0.899 rad/sであった。
方位RMSE 0.471度・最大2.371度、位置RMSE 0.573 mであったが、終点25.03 m手前で
900 wall秒の上限へ達したため完走不合格とした。車体接触0、±1 m以内94.80%である。
ログに入力pose途絶による停止・復帰が多発した。約0.2〜0.3倍速の計算に対し、
navigatorの単調時計による受信期限1秒が短かった。
共通launchのsimulationだけ受信期限を5秒へ変更し、realは1秒を保持した。
融合のROS観測時刻による入力期限とURG停止は維持する。環境差分をlaunchテストへ追加した。

評価器がGNSSモードでも未使用の真値publisherを登録しており、単一配信元検査が不合格になった。
on_poseのGNSS分岐ではpublishしないため真値混入はなかったが、登録自体を廃止した。
console_final_1800は受信監視修正のため早期中断した。完走試験として数えない。

## 6. 残る限界

- conservativeノイズは厳しめの仮定であり、実機データで同定した分布ではない。
- 方位σは推定値であり、真値誤差の上限保証ではない。
- GNSSとLIOの共通bias、車輪スリップ、GNSS長時間欠落は解消済みではない。
- 車体質量・重心・接触・モータ特性の実測校正、実機の配線・DDS・時刻同期は未検証である。
- ANT1→ANT2の補正が受信機に保存済みかは実機で確認し、二重補正を防ぐ。
- Qt offscreen試験はiPhone実機やMainWindow全画面の操作試験を代替しない。
- 今回の最終構成による全周再走と、歩行者・遮蔽・雨天を含む実環境検証は別に必要である。

## 8. 追加修正と完走確認（2026-09-14）

### 8.1 70 waypointの完走

console_timing_seed2はconservative seed=2、建物近傍FLOAT、180度方位反転5 wall秒、
1 ms・有限駆動制約・車輪退避を使用した。baseline変更はこの試験では行っていない。
70 waypointを欠落なく通過し、goal誤差0.316 m、車体接触0、UI連接合格となった。
真値時計247.4秒まで、wall時間約1,075秒であり、実時間性能の合格を意味しない。

| 指標 | GNSS | 未加工FAST-LIO | 融合 |
| --- | ---: | ---: | ---: |
| 方位RMSE [deg] | 14.327 | 1.093 | 0.476 |
| 方位最大絶対誤差 [deg] | 179.882 | 2.222 | 1.975 |
| 位置RMSE [m] | 0.970 | 10.944 | 0.673 |
| 位置最大誤差 [m] | 3.357 | 13.318 | 1.804 |

横ずれ最大1.217 m、±1 m以内92.81%であり、狭い通路での完全維持は未達である。
真値角速度最大0.932 rad/s、2 rad/s超の異常0。比較1,127点、欠測等88点を除外した。
FAST-LIOの最大観測間隔は1.3秒、融合は0.4秒であった。
停止・復帰は解消しておらず、pose受信監視の停止ログは初期待機を含め19回、
走行中の最長ほぼ静止時間は5.97 wall秒である。無停止完走とは判定しない。

### 8.2 時計・終点後の待ち・UI停止

上記70 waypoint試験は一時的な5 wall秒監視を使った。最終版ではnavigatorの
use_sim_timeに合わせて時計を選び、simulationはROS時計、realは単調時計で1秒を測る。
低速計算だけでは期限切れにならず、ROS時計が進んで本当に入力が途絶えれば停止することを
単体試験で確認した。70 waypoint全走行はこの最後の時計修正後には再実施していない。

console_short_fixed_seed3は終点FINISHEDへ到達したが、3 wall秒後の終了では低速計算の
制動待ちが不足し、停止判定に不合格となった。評価器を終点後2 ROS秒の待ちへ変更した。
また、UIのros2 launch停止は親へSIGINTを送り、launchに子停止を委譲する。
従来はプロセスグループとlaunchの双方からSIGINTが届き、終了処理中に再割込みされていた。
期限超過時のSIGTERM/SIGKILLによるグループ回収は維持した。

### 8.3 初期FLOATと正式UI

別の22 waypoint試験位置では初回からFLOATとなり、初期方位を確定できず待機した。
これは走行途中のFLOAT継続とは異なる。初回は良好FIX・方位・LIOを必要とする。
WAIT_INITIAL_FIXを配信してUIへ「初期FIX待ち」と表示し、方位に架空の0度を表示しない。
ROS入力途絶試験で、この初期待機表示とLIO欠落中の車輪継続・全入力途絶停止を確認した。

正式UI全体にはQt WebEngineが不足していた。sudoはパスワード認証で実行できなかったため、
aptの不足依存をローカル展開した。Qt 5の資源探索をqt.conf/QResourceで移設し、
Xvfbと既存conftestのfork隔離によるMainWindow 22件が合格した。
正式ui_qt_main入口でも4タブ、地図へのLLH重畳、融合方位の実受信を確認した。
UI後起動時の「準備完了」誤表示も、新鮮なfollower状態を優先して修正した。
画面右の画像viewerは別ノード未接続であり、カメラ画像の表示確認は含まない。
短区間は連接検査用経路であり、OSM上の表示を実コースの位置合わせ検証とは扱わない。

### 8.4 継続するLIO移動量不足と最終22 waypoint試験

console_final_clock_seed3では、受信監視の不要な停止はなくなったが、終点を3.877 m過走した。
1フレームごとの差分が小さいままLIO移動量が不足し、GNSSの0.5 m/s補正上限を上回った。
MotionGuardへ約1秒のLIO/車輪照合を追加した。並進差0.12+0.18dt m、
方位差0.1+0.1dt radを超える間は車輪を優先する。最大履歴1.5秒、整合復帰後の待機1秒とする。
診断にmotion_window_rejectionsを追加した。閾値は実測校正前で、車輪スリップは残る制約である。

evaluate_heading_replay.pyの--reselect-motionで、同じ失敗記録を再評価できる。
window_replay_toolの保存観測再生では位置RMSEが1.790→0.028 m、最大4.604→0.145 mになった。
これは良好FIXの保存データを用いたコア検査であり、閉ループ結果や実機精度ではない。

最終のconsole_window_seed3は、conservative seed=3・良好GNSS固定の22 waypointである。
建物近傍FLOATは8.1の別試験で扱い、この試験は移動量異常と時計・終了処理の回帰確認とした。
全waypointを通過し、goal誤差0.394 m、車体接触0、UI連接合格、終了状態STOPPEDとなった。
走行中の入力監視停止0、最長ほぼ静止0.266 wall秒である。初回の入力待ちは1回あった。

| 指標 | GNSS | 未加工FAST-LIO | 融合 |
| --- | ---: | ---: | ---: |
| 方位RMSE [deg] | 0.397 | 0.524 | 0.238 |
| 方位最大絶対誤差 [deg] | 1.111 | 0.826 | 0.633 |
| 位置RMSE [m] | 0.022 | 3.012 | 0.065 |
| 位置最大誤差 [m] | 0.054 | 6.280 | 0.209 |

経路横ずれ最大0.171 mであった。良好FIXではGNSS単独位置の方が良いことも併記する。
約1秒の運動照合・ROS時計への変更後に、70 waypointや全周を再走したわけではない。
最終版の閉ループ確認範囲はこの22 waypoint、長区間の根拠は8.1と全周記録再生である。

### 8.5 正式UIの最終確認と終了処理

qt_entry_releaseは正式入口から4タブ・環境名「デジタルツイン」・LLH・融合方位を
実際の模擬ROS graphから受信して合格した。起動設定タブの初期値がCLI環境を上書きする問題を
set_business_modeによる選択反映で修正した。iPhone実機の操作試験ではない。
共通起動の座標変換2ノードはSIGINTを正常終了として扱い、try_shutdownで二重終了を避けた。
