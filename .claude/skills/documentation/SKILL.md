# 文書種別

このリポジトリで扱う文書は 5 種別に限る。どの種別にも当てはまらない文書は作らない。
種別の定義、寿命、粒度の原則は `docs/ドキュメント整備方針.md` を正とする。
本スキルは各種別の**章立て雛形**を持つ。

| 種別 | 配置 | 雛形 |
| --- | --- | --- |
| 規約 | `docs/` | `assets/convention_template.md` |
| アーキテクチャ設計 | `docs/` | `assets/architecture_template.md` |
| 詳細設計書 | `src/<package_name>/docs/` | `assets/detailed_design_template.md` |
| 運用手順 | `README.md` / `src/<package_name>/README.md` | `assets/operation_readme_template.md` |
| 検討資料 | `docs/notes/` | `assets/note_template.md` |

廃止した種別がある。**検討記録と検証記録は作らない。**

- 選択肢の比較と判断を残す独立文書は作らない。判断を支える制約・限界・適用条件は、
  その判断が効いている恒久文書の本文へ書く。採用しなかった案は本文に含めない。
- ある時点の観測を凍結する文書は作らない。確認した条件と結果のうち現在も有効なものは
  恒久文書の確認方法として書く。過去の測定値は git 履歴が持つ。

# 書いてはならないこと

`CLAUDE.md` と `AGENTS.md` の「ドキュメント記述方針」を正とする。ここでは再掲しない。

文書に固有の適用として、**改版履歴の表・章を置かない。** git が持つ情報の劣化コピーに
なる。経緯を現在の仕様の記述へ変換する方法は `docs/ドキュメント整備方針.md` 4 章を参照する。

# 命名

- 日本語名を基本とする。内容を表す名詞句にする。
- **ファイル名と本文の見出しを一致させる。** 中身だけを書き換えて名前を据え置くと、
  読み手はファイル名から内容を判断できなくなる。
- 作業単位を名前に含めない。`_phase1` `_完全版` `_input` `_開発指示書` `_報告書` のような、
  実装完了後に意味を失う語を使わない。
- 同一対象の文書を複数作る場合は、扱う観点で分ける。phase や版で分けない。
- リンクの一覧だけを持つ文書を作らない。索引は `docs/README.md` と各 `README.md` に限る。

# 言語と文体

- 本文は原則日本語で記述する。常体「する」「を行う」を基本とする。
- チャット向け説明は丁寧語でよい。
- 英語の外部仕様、API 名、ROS メッセージ名、クラス名、関数名は保持してよい。
- 英語の原文を引用・保持する場合は、必要に応じて日本語補足を併記する。

# 配置

- ワークスペース全体に関わる文書は `docs/` 配下に置く。
- 特定パッケージに閉じる文書は `src/<package_name>/docs/` 配下に置く。
- 判断に迷う場合は「この文書はパッケージを削除したら一緒に消えるか」で判断する。
  消えるなら `src/<package_name>/docs/`、残るなら `docs/`。
- 恒久文書へ反映する前の分析・提案は `docs/notes/` に置く。恒久文書から `docs/notes/` へ
  リンクしない。参照は検討資料 → 恒久文書の一方向のみとする。

# パッケージごとの必須文書

| 文書 | 必須条件 |
| --- | --- |
| `README.md` | 全パッケージ。interface 定義のみのパッケージも含む |
| `docs/<名前>_詳細設計書.md` | ノードまたは非自明なロジックを持つパッケージ |

interface 定義のみのパッケージ（`tc_*_msgs`）は、README でメッセージ一覧と用途を示す。
各メッセージの配信様式・レートは `.msg` の先頭コメントに書き、README では重複させない。

# 詳細設計書

既存の `src/<package_name>/docs/*詳細設計書*.md` と README を確認し、そのパッケージの
章番号、用語、表形式、粒度に合わせる。既存文書に章立てがある場合は無理に全面改稿せず、
不足章を追加または既存章へ追記する。

既存の章立てがまだない場合は `assets/detailed_design_template.md` の 17 章構成を雛形と
して使う。該当しない章は「該当なし」と明記するか、省略理由を記載する。雛形をそのまま
丸ごと生成するのではなく、対象パッケージに必要な章だけを埋める。

**クラス名・関数名を列挙しない。** コードとドキュメントの二重管理になり必ず乖離する。
書くのはコードを読んでも分からないことに限る。

- なぜその構造を選んだか
- どの制約があってその実装になっているか
- 外部との契約（topic / パラメータ / ファイル形式）
- 状態遷移と例外条件
- 確認方法と、確認していない範囲

# コードとの整合

- コード変更により仕様、topic、パラメータ、状態遷移、QoS、launch 引数、ファイル構成が
  変わる場合は、関連文書の更新要否を確認する。
- コードと文書が矛盾している場合は、どちらを正とするか確認し、作業報告に明記する。
- 文書の改名・削除の後は `python3 tools/check_doc_links.py` でリンク切れを確認する。
- `setup.py` が `glob('docs/*.md')` で文書を install 対象にしているパッケージでは、文書を
  改名・削除すると `build/<package_name>/` に旧名の残骸が残り `colcon build` が失敗する。
  該当パッケージの `build/` を削除してから再ビルドする。

# 作業報告

文書を更新した作業報告では、参照した既存文書、追加・更新した章、コードとの整合確認方法、
ビルドまたは pytest を実行しなかった場合の理由を明記する。
